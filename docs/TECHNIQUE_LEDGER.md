# Blender technique ledger

This is Blendlink's living technical-art research queue. It converts expert
knowledge into bounded, testable compiler ideas instead of a pile of feature
suggestions.

- Last reviewed: 2026-07-27
- Detailed source mining: [A Version of Reality](research-version-of-reality.md)
  and [other expert Blender sources](research-expert-blender-sources.md)
- Competitive outcomes: [FEATURE_PARITY.md](FEATURE_PARITY.md)

## Intake contract

Every candidate needs:

1. a primary source and a clearly stated artist problem;
2. a route: Preserve, Realize, Bake, Runtime Recipe, Cache/Proxy, or Block;
3. a minimal `.blend` that demonstrates both the good case and its failure case;
4. a measurable benefit such as fidelity, iteration time, retained editability,
   payload, or runtime cost;
5. a recommendation: Prototype, Backlog, Adopted, or Reject; and
6. for a Needle comparison, separate relation (Match, Improvement, Boundary,
   Gap, or No analogue), implementation (Shipped, Prototype, or Future), and
   evidence (named fixture/command, last-pass date/toolchain, or Pending current
   run) under a stable capability ID.

No technique becomes a production feature directly from research. A prototype
must prove the route on the currently supported Blender version and compare its
output with the existing pipeline.

## Required Needle comparison gate

Every behavior-level change first answers four questions:

1. Does the currently inspected Needle addon/runtime implement an analogous
   behavior? Record the exact version and source path or upstream revision.
2. What does Needle actually do in code, including cleanup, failure, and edge
   behavior—not merely what its UI calls the feature?
3. Is Blendlink matching it, or improving it for a stated product-boundary or
   measured reason?
4. What focused differential fixture can make the Needle-style and proposed
   behavior fail independently?

The default is the proven Needle approach. A deviation is promoted only after
the ledger or a linked research note records primary-source evidence and the
focused test/prototype. Claims remain explicitly **Prototype** or **Future
Work** until that evidence passes. If Needle has no analogue, record that fact;
absence is not parity. Re-audit the comparison whenever the inspected Needle
version, pinned file bytes, runtime/build/Three dependency, source location, or
acquisition artifact changes. Verify the exact local identity with
`npm run verify:needle-baseline` before relying on an existing conclusion.

## Adopted result: procedural and instance evidence

The first diagnostics tranche is now a production compiler seam rather than a
collection of UI guesses. The addon and headless exporter call the same
read-only analyzer. Manifest `sceneDiagnostics` carries the complete
source/evaluated topology samples, dependencies, routes, stable instance
members, material and camera evidence, and measured draw consequences. The
generated website binding does not duplicate that potentially large tooling
record: versioned `runtimeDiagnostics` v1 projects only `lodChains` and
`instanceGroups`, the two inputs consumed by browser adapters.

Current runtimes retain one read-only migration path for older generated
bindings that still contain full `sceneDiagnostics`. A present
`runtimeDiagnostics` value always wins; unsupported versions or malformed v1
arrays fail loudly instead of falling back to stale legacy evidence. Package
runtime and regenerated binding therefore move together when the new contract
is adopted.

The boundary remains intentional. Fixed-topology deformation is reported as a
finite cache candidate but blocked until a named morph/VAT adapter and visual
gate exist. Changing topology, Simulation Zones, oversized/unproven ranges,
and movable-camera-dependent geometry block rather than freezing a plausible
frame. Shared mesh data remains ordinary addressable objects unless the website
explicitly opts into the reversible `InstancedMesh` adapter. Progressive-mesh
generation and arbitrary procedural runtime translation remain research items.

## Evaluation: AVR-001 Eevee UV-mesh capture

### What the source actually proposes

The source creates a mesh representation of the model's UV layout and renders
that flattened geometry with an orthographic camera in EEVEE. It is therefore a
render-to-texture technique, not Blender's native Bake operator. Its attractive
case is appearance that Eevee can render but Cycles cannot reproduce directly,
especially Shader to RGB stylization, procedural color, decals, and layered
superimpositions.

Blender's current documentation still describes native texture/light/AO/normal
baking as a Cycles operation, while EEVEE retains the EEVEE-only Shader to RGB
node. Blender 5.2 also still exposes Shader to RGB and orthographic cameras, so
the primitive mechanism remains plausible. Compatibility of the video's exact
Geometry Nodes group must still be proven in a reference file.

### Why it may fit Blendlink

- It could make fast Preview bakes much closer to an Eevee-authored viewport.
- It could capture material layers that currently fail when the pipeline forces
  them through Cycles.
- The flattened mesh can be generated in a temporary copy, preserving the
  artist's source graph.
- It naturally fits a named appearance-layer compiler better than a replacement
  for the existing lightmap baker.

### Why it must remain bounded

- World/object/camera-dependent inputs may change when geometry is flattened.
- AO, cast shadows, indirect lighting, selected-to-active projection, cage
  baking, and high-to-low normals require spatial/ray information this method
  does not inherently preserve.
- UV seams, margin generation, alpha coverage, mip safety, color management,
  and background bytes still need the same rigor as the current bake pipeline.
- A fast render is not useful if its output differs subtly from the artist's
  actual material at animation poses or reference cameras.

### Prototype acceptance criteria

1. Build a Blender 5.2 fixture containing ordinary PBR, Shader to RGB, decals,
   procedural UV/object/generated coordinates, alpha, and a known seam pattern.
2. Capture Base Color / Emission-style appearance through the UV-mesh route.
3. Compare it against the Eevee reference render and the current Cycles bake.
4. Measure wall time, edge coverage, background entropy, output bytes, and color
   error before and after the existing save/flatten/packing contract.
5. Adopt only for the semantic layers it reproduces reliably; report unsupported
   coordinate dependencies instead of silently producing a plausible wrong map.

Current recommendation: **Prototype as an optional appearance-layer backend;
do not replace Cycles light, AO, or normal baking.**

### Prototype 1 result — 2026-07-19

The runnable Blender 5.2 fixture lives at
[`experiments/eevee-uv-materializer-prototype`](../experiments/eevee-uv-materializer-prototype/README.md).
It constructs the UV canvas with Geometry Nodes and renders two atlas islands
through EEVEE.

- Decoded pixels were exactly deterministic across consecutive renders
  (`repeat RMSE = 0`). PNG file hashes differed because the files themselves
  contain changing metadata, so byte hashing the container is not a valid
  determinism test.
- Stable flat material regions matched a Cycles emission bake closely
  (`RMSE = 0.000411`). The all-interior error was `0.060050`, concentrated at
  procedural checker transitions where EEVEE raster antialiasing and Cycles
  bake sampling differ.
- Shader to RGB produced a valid UV-space capture, proving the unique EEVEE
  path rather than only reproducing a material Cycles already supports.
- The trivial portable material was much faster through Cycles (`0.008 s`) than
  warm EEVEE (`0.077 s`; `0.622 s` cold). Speed is therefore not an adoption
  argument without a representative complex-material benchmark.

Decision: **continue the prototype only as an EEVEE-only appearance
materializer.** Do not replace the Cycles lighting or portable-data paths. The
next gate is alpha/margin behavior, mirrored-island MikkTSpace normal detail,
coordinate-dependency blocking, and 1K/4K timing.
