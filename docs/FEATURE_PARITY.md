# Blendlink / Needle Blender feature ledger

This is a living competitive inventory, not a one-time research report.

- Last audited: 2026-07-26
- Needle addon inspected: 1.4.2, installed locally for Blender 5.2
- Blendlink version: 0.8.0 development tree
- Detailed UI notes: [research-needle-addon-ui-parity.md](research-needle-addon-ui-parity.md)

Update this table in the same change that materially changes a listed
capability. Re-audit the installed Needle source when its version, pinned bytes,
runtime/build/Three dependencies, source location, or acquisition artifact
changes; `npm run verify:needle-baseline` checks the exact identity recorded in
[`needle-baseline.json`](needle-baseline.json). That gate now also records
whether the packages form a coherent installation. The current inventory is
`integration=mixed-source`: package-level source conclusions are valid, while
the add-on-selected dependency lock now passes `npm ci` and `npm ls --all`.
End-to-end Needle export/build/runtime claims still require the authenticated
3.0.0 transform and a named browser differential.

## Status vocabulary

| Status | Meaning |
| --- | --- |
| Better | The relevant artist outcome exists and Blendlink intentionally presents or solves it more clearly. |
| Parity | The relevant outcome exists at roughly comparable quality. |
| Partial | Useful support exists, but an important part of the outcome is missing. |
| Gap | It fits Blendlink's promise and is not implemented yet. |
| Evaluate | It might fit, but needs an artist job and technical prototype before commitment. |
| Experimental | A bounded implementation or prototype exists, but its named visual, lifecycle, accessibility, or performance acceptance gate is incomplete; do not treat it as a release claim. |
| Out of scope | It belongs to a hosted engine or application, not the Blender-to-Three.js compiler. |

`Core` capabilities belong in the compiler/addon. `Adapter` capabilities may
ship as small optional Three.js helpers while keeping the output portable.

## Verification gate and claim boundary

Compiler/package claims are gated by `npm run test:full` on the supported Node,
Blender, Three, and Khronos KTX toolchain. That aggregate requires rather than
silently skips the real codec path and contains the first four bullets below;
it does **not** run Playwright or the external dogfood/demo portfolios. Release
readiness additionally requires the separately named site and demo browser
gates that follow. This ledger deliberately avoids a fixed unit-test count
because the suite grows with the feature surface. Required evidence includes:

- the unit/contract suite followed by required real KTX texture/HDR round-trip
  assertions in [the owned toolchain gate](../scripts/test-real-toolchains.mjs);
- clean Vanilla Three and React Three Fiber consumers built both from the
  workspace and from the packed npm tarball;
- [the headless addon contract](../packages/blender-addon/tests/run_headless.py),
  including isolated archive install/enable and the shared vocabulary cases;
- [the real appearance and lighting bake gate](../scripts/test-baked-e2e.mjs),
  including visibly different states, constant atlas corners, Meshopt,
  incremental rebuild evidence, and final-accessor atlas-layout evidence; and
- an isolated Next/R3F portfolio browser route loading the real KTX2 + Meshopt
  GLB, reaching the generated `onReady` boundary without failed asset requests
  or page errors, and passing the automated WCAG A/AA checks; and
- production Next/Chromium component and failure fixtures covering the
  21-component scene, semantic controls, real pointer/audio activation,
  renderer presented/full-quality evidence, retry, explicit base path, Blob
  worker CSP classification, WebGL creation/loss/remount, zero-size/empty
  Canvas evidence, and a real cross-origin response without ACAO; and
- exact packed-tarball Vite builds plus independent production Chromium
  HTTP/hash/WebGL/nonblank/error gates for Cube Diorama baseline, its explicit
  web-tuned derivative, and the deterministically generated 120-frame Splash
  source derivative; and
- a final-staged-GLB publication audit that refuses an empty default scene or
  mesh data reachable only from a non-default library scene, while accepting
  visible triangle, line, or point primitives and preserving `blendlink plan`
  for intentional helper/library files.

When `test:full` and every separately recorded production-browser/demo gate in
scope for the release are green on the current package, they support calling
the core compiler
**engineering-beta ready on the tested toolchain**. It does not prove
product-market fit or that artists prefer
every row marked Better. Those comparative claims remain hypotheses until the
[concierge, atlas-usability, competitive-switch, and interview thresholds](research-blender-threejs-market.md#falsifiable-validation-plan)
are run. Blender 4.2 and Node 22.15 are enforced compatibility floors but have
not yet received the same full matrix run. Reflection-probe authoring now has
a decoded scene-linear Blender 5.2 six-direction orientation gate plus exact
render/restore/publication evidence. The runtime CubeCamera/PMREM path also has
a real Chromium six-face, receiver-exclusion, visible-presentation, and cleanup
gate. Published-panorama loading, postfilter directional decoding, context
loss, and wider browser/device evidence remain future.

## Explicit non-parity groups

Needle's WebXR/AR/QuickLook, networking, voice chat, cloud, branded web menu,
animator state machine, runtime drag/drop, licensing, hosted deployment, and
application-framework/UI components are recorded here once rather than expanded
into hundreds of rows. Blendlink's component contract can preserve a custom
namespaced record, but adapter-extensible does not mean implemented. Multiplayer
records are deliberately excluded. These groups do not determine whether
Blendlink successfully compiles beautiful Blender scenes into portable Three.js
projects.

## Maintenance checklist

When a Blendlink feature lands:

1. update its row and link the implementation or verification evidence;
2. test the artist outcome, not merely the existence of a property;
3. compare the resulting Blender UI with the installed Needle addon;
4. move a row to Better only when the consequence is clearer or the workflow is
   measurably safer/faster;
5. add any newly discovered technique to the technique ledger before promoting
   it into this feature ledger.
