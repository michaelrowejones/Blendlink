# Static Euler rotation: source-only proposal

Status: research only, no implementation or numerical/support credit. No Blender process, render, browser or GPU job ran in this task. All primary source URLs, exact bytes and retained schema hashes are in [sources.json](sources.json), pinned to Blender `02f0899d78e374b63e7181d9061e1f7ab03419cc`. Upstream C++ is GPL-2.0-or-later; no derivative kernel is proposed.

## Native facts

`FunctionNodeInputRotation` has no inputs and one ROTATION output. DNA stores `NodeInputRotation.rotation_euler` as three zero-initialized floats. RNA exposes the storage as `rotation_euler`, a Float/Euler property. Its CPU builder reads that EulerXYZ triple and constructs a constant quaternion using `math::to_quaternion`. It has a CPU MF callback and no shader GPU callback. This property is not the output socket's three-value UI default, and neither is a four-component quaternion.

`FunctionNodeEulerToRotation` has one VECTOR3 `NodeSocketVectorEuler` input named Euler, default `(0,0,0)`, and one ROTATION output. Its CPU MF takes float3, constructs EulerXYZ and calls the same conversion. A GPU callback exists in source, but retained native catalog availability is compositor root/group only; it does not establish shader-tree support or GPU parity.

`to_quaternion(EulerXYZ)` halves the three angles, computes scalar float sine/cosine, stores four two-factor products, then combines them into W/X/Y/Z. There is **no normalization, canonicalization, angle wrapping or Euler-order branch** in this overload. The AngleRadian wrapper delegates to `std::sin`/`std::cos` on the stored float. Calling its result a separately normalized quaternion would be inaccurate.

## Proposed domain and bounded arithmetic argument

Initial source angles: each original Float32 word is raw +0 or **positive** `[2^-16,1]` radians. Negative angles, -0, subnormals, nonfinite values, fields, computed vectors and animation refuse. Keep the exact existing build/platform/CPU profile. Do not generalize to arbitrary Euler orders or shader contexts.

For a nonzero angle its exact halving lies in `[2^-17,0.5]`. In this interval the real sine is greater than `2^-18` and at most 0.5, while cosine exceeds 0.5 and is at most 1. These deliberately loose intervals tolerate ordinary native libm Float32 rounding by many orders of magnitude. The actual pinned libm/compiler stage still needs the independent native controls below; the C++ standard alone is not an exhaustive implementation error bound.

All stored sine/cosine inputs are positive or +0; the coarsest universal lattice needed for positive sine floats in the loose interval is `2^-41`, and for cosine floats it is `2^-24`. A three-factor product with at most two sine factors (the X/Z subtraction terms) therefore lies on a lattice no finer than `2^-106`. The W term with three sines reaches the coarser minimum magnitude `2^-54`, with no cancellation. Rounded two-factor products/ordinary outer products stay normal: their nonzero magnitudes are at least `2^-36` and `2^-54` respectively. Contraction of an outer multiply/subtract does not create a finer exact three-factor lattice than `2^-106`; nonzero cancellation residuals are still far above the Float32 normal threshold `2^-126`. With the stated operation structure and round-to-nearest, exact subtraction of equal nonnegative terms yields +0, not -0. There is no unary negation in the XYZ overload.

W is a sum with its cosine triple greater than `1/8`, so W stays strictly positive. There is no possible negative-W sign-canonicalization issue in this domain. Y is a sum of nonnegative products. **X and Z can be negative even though all source angles are positive**; their subtraction can also cancel. No componentwise positivity claim is made, and no cancellation epsilon or input quantization is proposed. This analysis does not license replacing native trig or reordering its polynomial in JavaScript.

The important qualification risk is storage: a private Float attribute and a native CPU compositor Float output can both canonicalize -0/subnormals. Agreement between those two alone cannot prove absence of a hidden sign. The bounded source-stage argument above is plausible, but must be accompanied by an independent raw-bit witness before promoting this slice.

## Small independent proof before a full matrix

1. Public raw-array storage canary for both producer classes: +0, -0, minimum/maximum subnormal and representative ordinary three-word inputs; classify stored bytes before any float promotion. Invalid classes refuse, source users/groups/context restore. No numerical support credit from this canary.
2. Actual Geometry CPU-MF and CPU compositor each feed every native RotationToQuaternion output into a **native Float Hash Value before any Float attribute/output carrier**. Native Value controls must distinguish +0/-0 and subnormals in that same transaction. Store Geometry hash as INT and compare the compositor hash through independent integer byte channels, avoiding INT-to-Float precision loss. Compare against the hash of the separately read candidate Float word; this detects a hidden pre-store -0 even if both ordinary Float carriers become +0. Reuse the retained raw-word transport research; Hash itself is an oracle diagnostic, not a newly supported port.
3. Per producer: zero identity; each positive axis at min, nextafter(min,+inf), 0.1, 1; two-axis zero patterns; all-min/all-one; mixed min/one; ordinary asymmetric non-half triples; and X/Z cancellation-neighbor triples generated from the analytic tan-half relation then stored as unmodified adjacent Float32 angles. Predeclare exact normal-or-+0 word equality; no tolerance expansion. Stop/narrow if the pre-storage hash contradicts the source argument.
4. After the native pilot succeeds, use existing family architecture for saved Final, group/reroute/property ownership, source mutation/cache guards, both actual APIs on Metal+SwiftShader, constant resize/DPR and repeated disposal. Do one combined frozen build and one full root transaction. No runtime Rotation opcode, per-frame native work or texture is needed.

If pre-storage signed-zero fidelity cannot be established cheaply, defer mixed Euler triples rather than guessing. The zero/all-positive single-axis subset has no cancellation and is a simpler bounded fallback (both classes could qualify only that partial scope). A pure opaque Rotation reroute/group identity adds no new useful native class and is not a substitute for a failed Euler conversion port.

## Retained native CPU witness pilot

`witness-pilot.json` closes the historical isolated research transaction; `witness-observations.json` retains all 58 settings and exact component/hash words. The third fresh run completed 356 tiny CPU compositor renders (8 calibration plus 58×6), 232 component comparisons and 232 pre-Float-store full INT hash comparisons with zero differences, no unexpected -0/subnormal/nonfinite outputs and zero GPU initialization calls. Both native producer classes passed the same 29 settings, including identity, positive single axes at minimum/next minimum/ordinary/maximum, asymmetric/minimum/maximum/symmetric triples, zero-axis exact cancellations, analytic cancellation Float32 neighbors and two actual opaque Rotation group instances. The Geometry path retains original producer classes; the compositor graph uses unchanged native nodes. No numerical Float coercion of the 32-bit hash is used: unsigned low16 and signed high16 are independently transported in exact Float32 channels and reconstructed as a uint32. Source hashes, actual binary/Node/helper identity, fresh native Python prefix archive and 356-EXR filename/content census are pinned. This remains research, not a supported SDK port or a saved Final/browser qualification.

The eight source-word calibrations independently reproduced the materialization hazard: Geometry Float attributes changed -0 and ±subnormals to +0, while native Geometry and CPU-compositor hashes before Float storage distinguished all eight original words and agreed with the manual hash. Every Euler component's pre-store hash equalled the hash of its ordinary stored candidate word in both contexts. This is evidence against hidden zero-sign loss in the measured cases; the bounded XYZ/RNE argument still supplies the proposed domain reasoning rather than extrapolating a finite census into universal proof.

Both initial public-array assumptions failed before rendering and are retained separately. InputRotation's property and the Euler socket's `default_value` are **mathutils.Euler**, not bpy numeric property arrays; neither offers `foreach_set/get`. The second producer is readable through its single homogeneous native `inputs.foreach_get('default_value', array('f'))`. For InputRotation, an owned native `NodeTree.copy`, pruning all but the selected copied node and homogeneous `nodes.foreach_get('rotation_euler', array('f'))` preserved all original +0/-0/minimum/maximum ±subnormal and normal canary words. The copy/read/remove sequence preserved the measured ownership snapshot repeatedly.

**Production blocker before implementation:** the InputRotation workaround must never copy an arbitrary authored containing tree blindly. Node count alone does not bound node storage or custom native/Python copy callbacks. A source route must close the entire containing tree's node classes/storage/item collections and bound its size before invoking native copy, or use a genuinely narrow native copy API. Unknown/custom nodes and unreviewed storage/selector-item sizes must refuse before copying. No authored source tree was admitted by this prototype; the pilot used owned known-node graphs only. EulerToRotation's direct homogeneous input collection reader has no whole-tree-copy requirement. Root should review this separation before authorizing SDK changes.
