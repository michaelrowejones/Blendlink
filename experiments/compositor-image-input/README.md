# Native static compositor Image input

The bounded live port reads authored **static Image/Alpha inputs** rather than
capturing a rendered compositor result. Packed/file sRGB PNGs and generated
sRGB byte buffers use a private native image-only normalization. Generated
Linear Rec.709/Non-Color float buffers retain their direct Float32 values.
No scene render, surface bake, artist node rewrite, or source-image save is
part of production extraction.

Input normalization uses different byte and float models. A universal
`Image.save_render` conversion is incorrect: native byte Linear Rec.709,
legacy data/alpha cases, and float-tagged sRGB can disagree with that route.
Only the measured combinations enter this model. Image filepath, format,
color space, alpha mode, dirty pixels, packed bytes and users remain unchanged;
owned decoder scenes/images are removed on success and failure.

## Canvas and resize contract

An Image has its own finite pixel canvas. It is **not stretched to the render
viewport**. Pointwise processing runs on that native canvas; only afterward is
it centered, cropped or transparently padded into the live drawing buffer.
Padding before an Invert/Exposure node would change the authored result.

Modern CPU realization retains Blender's Float32 matrix/coordinate stages,
parity correction and independently rounded bilinear neighbor indices. Simple
integer centering misses measured odd-window edge behavior. The source window
and textures remain fixed while resize updates bounded coordinate tables and
uniforms. Repeated sizes do not reupload those tables or change shaders.

Blender 4.2 currently requires even source and drawing-buffer dimensions.
Investigated odd legacy windows had unqualified/corrupt native results.
An unsupported resize raises a named limitation, preserves caller MRT/target/
clear state, and can recover at the next valid extent without rebuilding.
Legacy Composite Use Alpha is applied after finite-window realization. Its
disabled state makes the entire output opaque, including padded canvas pixels.
A separate 4.2 resize and actual Final packed-PNG proof retains that policy.

## Limits

- Source compositor device CPU; browser renderer WebGPURenderer with WebGPU or
  WebGL2. This does not qualify Blender's GPU viewport compositor or ordinary
  WebGLRenderer post processing.
- Bundled OCIO configuration with Linear Rec.709 working space. Custom input
  processing and unknown input transforms refuse.
- RGB/RGBA static, single-view, single-layer inputs. File/packed byte input
  currently requires PNG/sRGB. Generated byte input requires sRGB and Straight
  or Premultiplied alpha. Generated float input requires Linear Rec.709 or
  Non-Color/Raw; authored signed/HDR RGBA is retained.
- At most 4 megapixels per image, 8 megapixels of distinct decoded images per
  program, source dimensions <=4096 and output dimensions within 1..8192.
- Image/Alpha share one deduplicated input allocation. Native Float32 input
  values are losslessly zlib/base64 encoded inside the pinned presentation
  asset; Three's existing MIT fflate decoder adds no artist installation step.
  Decoded length/checksum/finite values and ownership are checked.
- Direct outputs and supported pointwise consumers can use matching image
  canvases. Mixed Render Layers, different image canvases, neighborhood filters,
  transforms, render borders/crop, sequences/movies/UDIM, image/node animation,
  multiview, multilayer and file-float display windows remain named refusals.

## Earned evidence

The durable native fixture produces **96 graphs on 4.2 and 97 each on 5.2/5.3**:
290 graph cases / 334 actual reference frames. It measures Image/Alpha,
file/packed/generated sources, RGB/RGBA PNGs, unsaved painted file/packed
buffers, alpha modes, signed/HDR float values, a losslessly compressed 1080p
background, pointwise grading and shared Image/Alpha use. Resize cases retain
one compositor through odd/even sizes, DPR 2, repeated extents and legacy
rejection/recovery, checking caller state and stable shader structure.

The built SDK passes **1,160 graph checks / 1,336 positive output-frame checks**
across recorded Apple M5 Pro Metal and LLVM SwiftShader, each using WebGPU and
WebGL2. Maximum absolute error is 2.384185791015625e-7 against the unchanged
2e-5 budget. The copied installed-package probe extracts an actual pinned
packed-image payload under a package-qualified namespace and verifies its
decoded size/digest and equality with canonical extraction on all three
versions. Source and fixture hashes accompany native references.

The separate Final fixture saves a real packed-PNG Blender scene. Production
Final sync publishes its GLB and presentation, verifies pins, preserves the
`.blend` bytes and matches the independently rendered native input. Browser
proof loads that exact GLB and pinned presentation through the production post
pipeline, including the display transform, and rejects a bad presentation pin.
All three native versions pass both recorded adapters/backends; the largest
Final pixel difference is 5.960464477539063e-8.
The additional 4.2 Final packed-PNG scene with Use Alpha disabled passes all
four adapter/backend profiles exactly, including opaque padding; source and
published-input preservation and bad-pin rejection remain required.

This is a partial input/canvas port, not universal image formats, working spaces,
video playback, mip/transform coverage or whole-renderer appearance parity.

## Preparation and responsiveness

The normal post-pipeline installer prepares Image inputs asynchronously before
finalization. It owns one opaque preparation per install attempt. The signal
already used by the compiled-scene transaction cancels decoding, including a
pending application scheduler. A failed or cancelled replacement leaves the
previous pipeline usable. Handles are bound to the original program and image
bytes, reject mutation/cross-document/disposed/forged reuse, and release CPU
references after graph construction. Textures then own their Float32 arrays.
There is no global decoded-image cache and the published IR/pins are unchanged.

Base64 conversion uses feature-detected native conversion or an indexed
fallback. Native DecompressionStream is fed bounded 2KiB input pulls; browsers
without it use Three's existing streaming fflate. Checksum and finite scans
also cooperate with a default 4ms work target. A whole-Blob DecompressionStream
prototype produced a 150ms task and was rejected; an asynchronous API alone
did not make that path responsive. The synchronous decoder/builder remain
compatible for explicit low-level callers; the normal installer uses prepared
arrays and does not decode again during finalization.

The 1920x1080 case retains 33,177,600 decoded bytes and 2,383,040 compressed
bytes. Browser phase measurements found callback base64 conversion cost
57–62ms versus 3–6ms indexed / 0.5–1.3ms native, and callback finite scans
30–33ms versus 4–5ms indexed. Those changes alone reduced synchronous decode
from 180–188ms to 104–114ms; that still blocks an interactive preview.

The actual pinned 1080p-input Final fixture now measures preparation, finalization,
GPU rendering/readback, repeated replacement and cancellation separately.
It processes the full native-sized input/RTT and crops to a 16x8 output canvas;
this timing corpus does not qualify a 1080p final drawing-buffer deadline.
Recorded Apple Metal and SwiftShader runs on both browser APIs retained
16.8ms preparation RAF gaps, no preparation long tasks, cancellation/rejection
within 22ms for a 16ms scheduled request, exact last-good pixels, and unchanged
GPU texture counts. The native-stream phase corpus observed 4.1–5.3ms maximum
CPU slices. Preparation trades throughput for responsiveness: measured native
stream preparation took about 0.35–0.46s; feature-disabled streaming fallback
about 0.50–0.70s. Reapply remains cancellable throughout that interval. These
are local measurements, not timing guarantees on other hardware or workloads.

Cold shader compilation/texture upload is a separate limitation. A retained
early Metal/WebGL run produced a 166ms post-preparation task; later runs did
not. Three's public scene compileAsync does not compile the RenderPipeline's
private final quad/RTT stack. These results do not guarantee a universal
first-frame GPU deadline or eliminate browser/driver initialization stalls.

`performance.js` deliberately reproduces synchronous phases for measurement;
its resulting long tasks are not the normal installer path. The cancellation
timestamp is taken before pixel verification. Use the Final fixture's
`installationTimings` for the actual application path.

## Fixed-image rendering and full-canvas proof

An explicit allowlist permits caching only immutable Image-only pointwise
programs with no scene passes. Unknown/future, scene, spatial and neighborhood
operations stay uncached. The native input canvas renders once per renderer
using RTT's public `autoUpdate` / `textureNeedsUpdate` contract. Context
restoration invalidates that renderer; disposal removes its owned listener.
First-draw failure remains dirty for a later retry. Changed publication or
reinstallation creates a fresh graph and target rather than reusing old pixels.

Equal drawing-buffer/native-image extents use a real uniform-controlled `If`
branch to copy the RTT pixel. The unequal branch retains the original four
samples and Float32/parity stages. Resize/DPR tests assert both unchanged final
shader structure and exactly one native input pass initially, then zero repeat
input passes, including resize away/back and invalid-resize recovery. Native
signed/HDR RGBA and alpha cases remain part of the 290-graph matrix.

The additional full-canvas fixture uses an actual **1920x1080 drawing buffer,
CSS canvas and viewport** on Blender4.2/5.2/5.3 Final scenes, with recorded
Metal and SwiftShader adapters and both WebGPU/WebGL2. All 12 cases compare
five full native output frames (124,416,000 pixels total); maximum absolute
error is 5.960464477539063e-8. Native input SHA256, source preservation, actual
GLB/presentation pins, cancellation, replacement and GPU resource ownership
remain required. A separately saved/exported, differently painted 5.3 packed
image supplies a distinct pinned presentation: its cancellation preserves the
old pixels, and successful reinstallation must match the new native pixels.

Binary native reference files avoid JSON/Playwright transport of millions of
floats. Oracle fetching/hashing/calibration and all GPU readback/comparison run
outside the user-facing measurement windows. Those windows cover normal canvas
rendering during preparation, frame submission and the next animation frame.
The next animation frame is scheduling evidence, not a GPU-completion/paint
certificate. Recorded steady UI gaps are about16.8ms and cancellations about
21–22ms. A cold Metal/WebGL submission still produced a111ms task in one run;
it is retained, so there is no universal first-frame deadline claim.

Default macOS Chromium headless-shell Swift WebGPU canvas presentation failed
with Skia `CompoundImageBacking` / `kDissociateMailboxForPresent`, followed by
InstanceDropped during verification. Tiling readback, pausing diagnostic RAF
rendering and retaining adapter/device objects did not resolve it. Full
Chromium with an explicitly requested SwiftShader adapter passes the same full
33,177,600-byte readback and visible-canvas proof. That shell failure is retained and is
not represented as an image math fix. The shell's separate offscreen matrix
remains an independent correctness check.

## Reproduce

Use a built worker and an actual Blender executable:

```sh
npm run build
BLENDLINK_COMPOSITOR_IMAGE_REFERENCES="$PWD/artifacts/image/cpu" \
  /path/to/blender --background --factory-startup --python-exit-code 1 \
  --python packages/blender-addon/tests/compositor_image_check.py
node experiments/native-compositor-differential/run.mjs --built \
  --out artifacts/image/browser artifacts/image/cpu
```

Repeat native generation for 4.2/5.2/5.3 and pass all reference directories to
the browser runner. Repeat playback with
`BLENDLINK_TEST_CHROMIUM_CHANNEL=chromium`; verify the recorded adapter.
Default native success sentinel: `BLENDLINK_COMPOSITOR_IMAGE_PASSED`.
The positive source family is CPU-only; GPU refusal is tested inside it.

For actual Final publication/pipeline proof:

```sh
export BLENDLINK_COMPOSITOR_IMAGE_FINAL="$PWD/artifacts/image/final"
export BLENDLINK_COMPOSITOR_IMAGE_BLENDER=/path/to/blender
"$BLENDLINK_COMPOSITOR_IMAGE_BLENDER" --background --factory-startup \
  --python-exit-code 1 --python experiments/compositor-image-input/final_scene.py
BLENDLINK_COMPOSITOR_IMAGE_BUILT=1 node packages/blendlink/scripts/run-vitest.mjs \
  experiments/compositor-image-input/export.test.ts
node experiments/compositor-image-input/run.mjs --built
```

Set `BLENDLINK_COMPOSITOR_IMAGE_1080P=1` before saving the Final fixture to run
the large-image installation/cancel/reapply proof. Use
`BLENDLINK_IMAGE_FORCE_STREAM_FALLBACK=1` for explicit native-stream/native-base64
feature-disabled playback. Optional
`BLENDLINK_IMAGE_PERFORMANCE_PROGRAM=/absolute/path/to/packed-1080p-crop.json`
adds isolated base64/inflate/checksum/finite timing using a native reference
from the regular Image corpus. Reports and immutable runtime snapshots retain
separate performance/fallback suffixes.

Set `BLENDLINK_COMPOSITOR_IMAGE_FULL_VIEWPORT=1` alongside the1080p flag before
native fixture generation/export to measure the full drawing buffer. A second
fixture/export directory generated with
`BLENDLINK_COMPOSITOR_IMAGE_PATTERN_SHIFT=97` supplies replacement input; pass
it to playback with `BLENDLINK_IMAGE_REINSTALL_DIR=/absolute/replacement/dir`.
For full Chromium software playback:

```sh
BLENDLINK_IMAGE_PROFILE=chromium-swift \
BLENDLINK_TEST_CHROMIUM_CHANNEL=chromium \
BLENDLINK_TEST_CHROMIUM_ARGS='["--use-angle=swiftshader","--use-webgpu-adapter=swiftshader"]' \
node experiments/compositor-image-input/run.mjs --built
```

Inspect the recorded adapter; the profile label alone is not evidence. Optional
`BLENDLINK_IMAGE_BACKENDS=webgpu` and `BLENDLINK_IMAGE_READBACK_ROWS=32` isolate
one backend or use tiled diagnostic readback without changing UI rendering.
